# 01_封面

这份汇报介绍的是子宫超声辅助诊断系统，一个面向医院妇科超声场景的多模态 AI 辅助工具。它的定位不是替代医生，而是在真实检查流程中，把超声图像、检查文字、患者级聚合结果和可解释材料组织成一个可复核的闭环。接下来我会从临床目标、系统能力、模型架构、工程部署和使用边界几个层面展开。

# 02_临床背景与目标

这个项目的核心目标，是从单张影像的模型判断，走向患者级的辅助决策。真实超声检查通常包含多张切面图像，也包含检查方式和检查所见这些文本上下文，所以系统需要同时处理图像、文本和多图聚合。更重要的是，AI 输出必须能够被医生复核，因此 Grad-CAM、PDF 报告、历史记录和医生判断入口都是产品闭环的一部分。

# 03_系统能力地图

系统价值来自模型能力和工作流能力的组合，而不是单一分类器。单例推理覆盖医生现场上传和患者级结果，批量推理覆盖后台成批分析，结果解释提供逐图预测和热力图，病例与报告负责留档和沟通，管理保障则处理认证、审计、指标和备份。五类能力围绕患者级闭环协同工作，才适合进入院内使用流程。

# 04_V2多模态模型架构

V2 模型采用图像主导的多模态融合架构。图像侧使用 EfficientNet-B3，把 300 乘 300 的 RGB 图像编码成 1536 维特征；文本侧使用阿里医学 BERT，用 CLS 向量表示检查方式和检查所见。随后 ImageDominantGatedFusion 以图像为主导融合文本上下文，再通过 512 到 256 到 3 的分类器输出正常、子宫内膜癌和息肉三类概率。当前训练规模为一万余例患者和约十九万六千张图像，推理使用 Fold 3 的 EMA 权重。

# 05_单例推理流程

单例推理的设计重点是让医生现场操作不被长请求卡住。医生填写病例编号、选择检查方式、上传一到三十张图像，可选填写检查所见；提交后系统使用 idempotency_key 避免重复病例，并立即返回 task_id。前端持续轮询 queued、running 和 done 等状态，后台逐图推理并聚合为患者级结果。最终页面展示概率分布、逐图预测、Grad-CAM、医生判断入口和报告入口。

# 06_批量推理与优先级队列

批量推理解决的是后台成批患者分析的问题，但它不能影响医生的即时操作。批量任务通过 ZIP 和 manifest.csv 上传，系统按患者目录拆分，再生成逐图任务和患者级汇总。队列层采用优先级机制，单例任务 priority 等于零，批量任务 priority 等于五，因此现场单例请求可以优先进入模型 worker。这样既能跑批量，又不会让临床交互被后台任务阻塞。

# 07_解释与报告闭环

系统输出需要能被医生理解和复核，所以结果呈现分为预测、解释和报告三个层次。预测层给出患者级三分类概率，解释层保留每张图的预测结果和 Grad-CAM 热力图，报告层生成中文 PDF 便于归档和沟通。这里的关键原则是，模型结果只是风险提示和复核参考，医生判断和临床流程仍然是最终依据。

# 08_技术架构

工程架构围绕可部署、可追踪和可恢复设计。前端使用 React、TypeScript 和 Vite，负责单例、批量、历史和管理界面；后端使用 FastAPI、SQLAlchemy 和 SQLite WAL，负责 API、认证、审计和静态服务。推理队列通过 priority heap 和单 worker 串行调用模型，模型服务基于 PyTorch CPU、EfficientNet-B3 和医学 BERT。存储层包括 SQLite、uploads、gradcam 等目录，运维层通过结构化日志、request_id、健康检查和指标接口来支撑排查。

# 09_数据性能与部署

生产部署要重点关注资源、时延和恢复能力。推荐配置是八核以上 CPU、十六 GB 内存和两百 GB SSD，最低配置可以是四核、八 GB 和五十 GB。模型加载大约需要两 GB 内存，CPU 推理约一点二秒每张图。部署上，Linux 推荐 systemd，Windows 可以使用 NSSM；生产环境建议加 Nginx HTTPS，并开启 COOKIE_SECURE、HSTS 等安全配置。备份方面，系统通过 SQLite 热备和 uploads 增量 rsync 保留三十天，并建议定期做恢复演练。

# 10_安全审计与运维保障

临床系统上线后，安全网比功能列表更重要。认证侧使用 bcrypt、HttpOnly、SameSite、失败锁定和强制改密；审计侧记录登录、登出、创建病例和用户管理等关键操作，并支持 CSV 导出；可观测侧通过 structlog JSON、request_id、健康检查和指标接口定位问题；恢复侧依赖 backup.sh、runbook 和定期恢复演练。这样系统不仅能推理，也能在出问题时被解释和恢复。

# 11_临床使用边界

这套系统必须始终明确自己的边界：AI 输出是风险提示，不是最终诊断结论。产品文案和演示材料都应该使用“预测概率”“风险提示”“复核参考”这样的表达，避免“确诊”“替代医生”“自动诊断”等绝对化措辞。最终诊断仍依赖医生判断、病理结果和完整临床流程，同时需要持续监控数据漂移、异常病例和模型误差。

# 12_后续演进路线

后续演进建议从可用系统走向可验证、可集成和可持续改进。近期重点是真实病例验证、界面细节、报告模板和部署文档；中期重点是接入院内账号、影像系统或数据归档流程，让系统更顺滑地进入医院环境；长期则要建立模型版本治理、质控面板，并考虑更多病种或多中心验证。真正的交付终点，是让 AI 能力稳定进入临床流程。
